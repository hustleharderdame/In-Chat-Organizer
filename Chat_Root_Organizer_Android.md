# [[Chat_Root_Organizer_Android]]

owner:: [[Damien_Brock]]
serves:: "[[Chat_Root_Organizer_Service]] v1.0.0"
device:: Moto G · Termux proot Ubuntu · Flask on `127.0.0.1:8410`
status:: #status/active

**Two front-ends, one implementation.** The PWA is the entire UI. The Android
app is a WebView over it plus a share target. There is deliberately no native
re-implementation of the graph views — a second one would have to be changed
twice for every node-card tweak.

## 1. Why a PWA at all

The Flask server runs **on the phone**. `127.0.0.1` is a secure context in
Chrome, so the PWA is installable to the home screen with an icon and a
standalone window — no signing, no sideloading, no Play Store, and it updates
the moment the Flask app does.

The APK exists for the things a PWA on Android still cannot do: appear in the
system **share sheet**, and survive Chrome being cleared.

## 2. The PWA

source:: `chat_organizer/web/`

| File | Role |
|---|---|
| `app.html` | whole app — shell, styles, logic, no framework, no CDN |
| `manifest.webmanifest` | name, icons, `display: standalone` |
| `sw.js` | service worker |
| `icons/*.png` | generated by `tools/make_icons.py` |

* **Three tabs.** Graph (all nodes, tag-filtered), Tasks (open, grouped by root),
  Capture (paste a bridge block or type a thought).
* **No dependencies.** One file, inline CSS and JS. A CDN would break the moment
  the phone is offline — and the whole point is that this works with no network.
* **Theme-aware**, phone-first, verified to 320px with no horizontal scroll.
* **Ambiguity is resolvable from the phone.** When a capture matches two nodes,
  the candidates render as buttons; tapping one calls `POST /ingest/answer`.

### Service-worker caching rule

shell:: cache-first — the app opens instantly, and still opens when Termux is stopped
api:: **network-only** — a cached `/nodes` would quietly lie about what was filed

That second line is the important one. Stale graph data is worse than no graph
data, so API responses are never served from cache; when the server is down the
app shows its own "can't reach the organizer" panel instead.

## 3. The Android app

source:: `android/`

* `MainActivity.kt` — WebView + pull-to-refresh + a real offline screen (the
  most likely failure is simply that Termux isn't running, so it gets a retry
  button rather than a browser error page).
* `ShareActivity.kt` — share target. Select text in any app → **Share → Capture
  to graph** → it posts to the same `/ingest` endpoint the Capture tab uses.
  A second *caller*, never a second implementation.
* Launcher icon is an adaptive vector, so there are no binary drawables to keep
  in sync with the PWA's PNGs.

### Cleartext is loopback-only

`usesCleartextTraffic` stays **false** in the manifest; `network_security_config.xml`
re-enables cleartext for `127.0.0.1` and `localhost` and nothing else. The
organizer speaks plain HTTP because it never leaves the device — that is not a
reason to let the app speak plain HTTP to the whole internet.

### Building the APK

> **Not built in this repo.** The session that wrote this had no network access
> to `dl.google.com`, so the Android SDK, `aapt2` and the Android Gradle Plugin
> could not be fetched. The Gradle DSL and every XML file are validated; the
> Kotlin is **uncompiled**. Expect to fix a small thing or two on first build.

```bash
cd android
./gradlew assembleDebug      # app/build/outputs/apk/debug/app-debug.apk
adb install -r app/build/outputs/apk/debug/app-debug.apk
```

Needs JDK 17+ and the Android SDK (API 34). Gradle itself comes down via the
committed wrapper.

## 4. Write endpoints

These are the scope expansion beyond [[Claude_Code_Implementation_Report]],
which specified a read-only HTTP surface with ingestion as a Python call.
Captured from the phone, ingestion has to cross HTTP.

route:: `POST /ingest` — `{"text": "...", "source_chat": "phone"}`
route:: `POST /ingest/answer` — `{"chosen": {...one candidate...}}`

**Both refuse a non-loopback peer with 403.** Reads stay open so a desktop on
the same network can look at the graph; nothing that mutates it will answer
anyone but this device. `is_loopback` is unit-tested against IPv4, IPv6,
IPv4-mapped-IPv6 and unparseable peers, and treats unknown as untrusted.

Ingest routes through the ordinary `Organizer.ingest`, so a paste gets the same
classification, reconciliation and ambiguity rules as an in-chat turn.

## 5. Thread safety

Found by running the real server rather than the test client, which dispatches
in the calling thread and so can never see it:

> `sqlite3.ProgrammingError: SQLite objects created in a thread can only be
> used in that same thread.`

Any WSGI server — the Flask dev server included — handles requests on worker
threads, while the connection is opened once at startup. So:

* `db.connect` passes `check_same_thread=False` and sets `busy_timeout=5000`
  (the organizer shares one SQLite file with the rest of [[DDB.OS]]; without it
  another component's write surfaces here as an immediate "database is locked").
* `Organizer` holds an `RLock` and takes it in every public method. The lock
  lives there because `Organizer` owns the connection — `db` stays a thin,
  lock-free data layer.

Pinned by two threaded regression tests.
